# Internationalization

> Status: Rule

OpenExcel is an internationalized application. User-visible language belongs
to the Web presentation layer and must not be embedded in domain or transport
code.

## Required behavior

- New and modified comments, docstrings, and code-facing explanations must be
  written in English.
- New user-visible copy must be represented by a stable i18n key. This includes
  component text, form labels, validation feedback, toast messages, dialog
  titles and actions, placeholders, tooltips, document titles, and `aria-label`
  values.
- Use the existing Web i18n runtime and locale resource files. Do not add a new
  translation helper, inline fallback sentence, or feature-local translation
  table.
- `t(key, vars?)` is the supported call shape. Do not add new uses of
  `t(key, fallback)` or equivalent fallback APIs.
- Locale resources must keep the same key set. Add or update every supported
  locale in the same change; the resource parity test must continue to pass.
- Missing keys must remain observable in development or tests. Do not hide a
  missing translation by silently falling back to another user-facing
  sentence.

## Error boundaries

- Server, Core, and Agent code must not return UI-localized sentences as their
  public contract.
- Predictable errors should expose a stable `errorCode` and structured `params`
  at the boundary. The Web layer maps that code to a locale resource.
- Logs and internal diagnostics use concise structured English. They may carry
  raw business data, identifiers, and provider details, but must not be used as
  display copy.
- During the migration, Web API clients may read the existing string-based
  `{ error: string }` response for compatibility. New endpoints should use the
  structured envelope and existing endpoints should migrate when touched.

## What may remain localized data

Workbook contents, imported Excel values, user-entered names, demo fixtures,
sample data, formula text, and test assertions that model real business data
are not UI copy. They may remain in Chinese or another language. Do not replace
real data with translations merely to satisfy this rule.

## Incremental migration

This rule applies immediately to new and changed code; it does not require a
repository-wide rewrite. When touching a legacy file:

1. Move the user-visible strings in the changed path into locale resources.
2. Replace server or domain sentences with a stable error code and parameters
   when that boundary is part of the change.
3. Add or update focused tests for resource parity, error mapping, or the
   affected user workflow.
4. Remove the old fallback or hardcoded sentence once no caller needs it.

Do not do a broad translation rewrite as unrelated cleanup. Keep the migration
reviewable and preserve business data exactly.
